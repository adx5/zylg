[Heading 2] 5.2 P0/P1 缺陷详述
[Heading 3] BUG-01（P0，安全）跨角色越权读写商家岗位数据
现象与影响：使用服务商身份（13900030001）的合法 token 直接调用商家接口，可读取其他商家的岗位管理数据，并可对他人岗位执行下架、上架等写操作。已复现：GET /api/jobs/my-list 返回 merchant_id=48 的 5 个岗位（含 risk_score、promotion_points 等内部字段）；PUT /api/jobs/83/offline 成功下架他人岗位（测后已通过 PUT /jobs/83/publish 恢复上架）；PUT /api/jobs/received 同样未做角色校验（返回 200）。该缺陷可被任意低权限账号利用，造成全平台商家岗位被恶意下架或数据泄露，属于上线阻断项。
复现步骤：1) 以 13900030001 登录获取 provider token；2) GET /api/jobs/my-list?page=1&size=100，观察返回的 5 条岗位记录中 merchant_id=48；3) PUT /api/jobs/83/offline，返回 200「岗位已下架停招」；4) GET /api/jobs/83 确认 publish_status 变更。
修复建议：在 /jobs/my-list、/jobs/{id}/offline、/jobs/{id}/publish、/jobs/received 等商家资源端点统一增加角色校验（仅 merchant）与资源归属校验（job.merchant_id 必须等于 token 中的商家主体），建议以中间件方式全局拦截而非逐点修补，并对存量接口做一轮越权扫描。
[Heading 3] BUG-02（P1，功能）完工结算闭环断裂，积分无法发放
现象与影响：求职者完成用工后提交完工申请（PUT /jobs/application/{id}/finish），投递状态正确流转为「申请结单中」（status_code=7），但商家侧无法完成结算：1) GET /api/jobs/pending-reviews 不返回该单据（新单 81 缺失，仅返回种子单 60）；2) 商家端 POST /api/jobs/review {application_id:81} 返回 400「单据尚未完工，暂不可评价」。对种子单据 60 执行同样评价则成功返回「评价提交成功」。结果：真实走完业务流程的单据永远无法结算，worker 的 +50 积分激励无法到账，直接破坏平台核心激励闭环。
复现步骤：1) 求职者 13900010002 报名岗位 474 并被录用；2) 求职者在「我的投递」点击「申请完工结算」，确认后状态变为「申请结单中」；3) 商家 13900020001 打开「用工结算与评价」，履约中列表无该单据；4) 直接调用 POST /api/jobs/review {application_id:81, rating:5}，返回 400「单据尚未完工，暂不可评价」。
修复建议：核对 finish 接口落库的状态字段与 review/pending-reviews 查询条件（疑似 status_code 写入值与查询期望值不一致，或完工标记落在不同字段）；修复后以「报名→录用→完工→结算」全链路回归，并用新单据验证积分到账与通知生成。
[Heading 2] 5.3 P2 缺陷
[Heading 3] BUG-03（P2，功能）服务商主页渲染原始接口错误文本
访问 /provider/homepage 时页面直接渲染未处理的 JSON 校验错误文本（如 [ { “type”: “int_parsing” ...），同时抓到两个异常请求：GET /api/services/my-profile 返回 404，GET /api/services/providers/undefined 返回 422（前端将 undefined 拼入路径）。用户可见原始报错，观感差且暴露接口细节。建议：前端修复 id 取值链路与 404 兜底；后端补齐 my-profile 对未建档案服务商的默认返回；页面增加错误边界兜底 UI。
[Heading 3] BUG-04（P2，功能）求职者端无消息中心入口
后端为求职者生成「收到面试邀请」「完工结单已确认」等站内通知（求职者 0001 有 70 条未读），但求职者端前端没有任何消息入口：notifications 相关接口仅在商家前端被引用，/worker/messages 路由不存在（渲染白屏）。求职者只能进入「我的投递」列表翻找才能发现面试邀请，极易错过面试。建议：求职者端增加消息中心页面与底部导航/首页红点， unread-count 已有接口可直接复用。
[Heading 2] 5.4 P3 缺陷
[List Paragraph] BUG-05（P3，一致性）多处统计口径不一致：/admin/stats 的 pending_companies=1，而审核中心企业 Tab 实际展示多张待审核卡片；GET /jobs/received-count=26、GET /jobs/received 返回 65 行、商家首页「收到简历 0」三个口径互不一致。建议统一统计口径并在文档中明确定义（如是否含已处理/不合适记录）。
[List Paragraph] BUG-06（P3，健壮）自动注册产生空壳企业备案：任意手机号登录即自动建号，merchant 角色登录会自动创建名称为空的企业备案记录（审核中心显示为「请完善名称」），本次测试期间产生多张空壳待审卡片污染审核队列。建议：企业备案改为商家主动提交创建，或对自动创建的备案打「未激活」标记不进入待审列表。
[List Paragraph] BUG-07（P3，体验）未注册路由白屏：/worker/messages、/merchant/settlement、/merchant/balance 等未在前端注册的路径渲染纯白屏，无 404 或返回引导。建议增加全局路由兜底页。
[List Paragraph] BUG-08（P3，性能）部分页面首屏加载超过 2 秒：岗位详情等页面首次进入偶现「加载中…」停留 2.5 秒以上（接口本身 200 且响应快，属前端渲染时序问题）。建议优化详情页数据加载与骨架屏体验，弱网下建议增加超时重试。

[Heading 1] 六、风险评估与遗留问题
[Heading 2] 6.1 上线风险
内容合规风险（高）：站内存在大量明显可疑的存量测试岗位，如「高薪诚聘KTV陪酒人员-日结3000元-详情加微信abc12345私聊」等典型招工诈骗话术样例，且岗位风控字段 risk_status 均为 unchecked、风控接口对新发布岗位返回 decision=pass。正式环境若带入此类数据且风控未启用内容扫描，存在重大合规与舆情风险。建议上线前清空种子数据，并对存量岗位执行一次风控回扫。
激励体系可信风险（中）：种子账号携带初始积分（如 1755 分）但积分明细无来源流水，影响审计可追溯性；建议补齐种子数据的积分流水或统一清零。
[Heading 2] 6.2 未覆盖范围
以下内容不在本次测试范围或未能验证，需另行安排：短信/微信登录通道（前端提示「待接入」）、真实支付与推广余额充值（当前为线下充值）、图片上传的内容审核有效性、性能与并发压测、iOS/Android 真机兼容性、city_gov 属地数据隔离的深度验证（其可见数据与总台一致，属权限收敛问题，建议开发确认设计意图）、消息推送通道、以及 BUG-01 修复后对全部商家资源接口的越权回归。
[Heading 1] 七、测试结论与建议
[Heading 2] 7.1 结论
平台四端主流程骨架完整、跨端状态机运转正确，防御性设计水平较高，具备继续迭代的良好基础；但 BUG-01（越权读写）与 BUG-02（结算闭环断裂）两项严重缺陷阻断上线。测试结论为：不通过（暂不具备上线条件），修复 P0/P1 并回归后可达到有条件通过标准。
